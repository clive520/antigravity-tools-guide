Linear 擴充功能實戰指南
Issue 結構化追蹤、Sprint Cycles 與產品藍圖

透過 Antigravity 的 Linear 專屬生態外掛，AI Agent 深度融入敏捷研發流程：自動將混亂的使用者需求拆解為驗收準則清晰的 Issue、合理分配 Sprint 週期與估點 (Story Points)、關聯 GitHub PR 自動更新看板狀態，並追蹤 Roadmap 戰略進度。

1. 功能概述與生態定位

Linear 是現代全球頂尖科技公司（如 Vercel、OpenAI、Retool、Cash App）首選的軟體開發追蹤工具。相比傳統笨重的專案軟體，Linear 具備毫秒級同步、簡約設計與高度結構化的實體關聯。在 Antigravity 中連接 Linear，可大幅縮短工程師與產品經理在「記錄進度」與「寫程式」之間的摩擦力。

自然語言拆解 Issue
AI 自動識別需求痛點，自動補齊重現步驟、驗收標準 (AC) 與預估複雜度 (Estimation)。
Cycles 節奏與燃盡分析
即時掌握團隊 2 週 Sprint 週期負載，自動預警範圍蔓延 (Scope Creep) 與關鍵路徑阻礙。
代碼庫與 PR 自動閉環
透過 Git 分支名稱或 Commit Message 自動關聯，當 PR 審閱通過即自動推進至 In Review 或 Done。

2. 這個功能能做什麼？

Linear 整合套件賦予 Antigravity 4 大工程組織協作能力：

結構化 Issue 與 Sub-issues 樹狀管理

將龐大 Epics 拆分為父子 Issue，設定優先級（Urgent、High、Medium、Low）、標籤（Bug、Feature、Refactor）與指派人。

Sprint Cycles 自動化排程與速率預測

自動將待辦工單分配進當前或未來的 Cycle，計算團隊歷史速率 (Velocity)，避免工程師超額承諾造成延宕。

Roadmap 產品藍圖與里程碑彙報

在季度維度上追蹤多個專案目標 (Milestones)，AI 一鍵彙整跨團隊進度，向領導層發送結構化專案狀態週報。

雙向 Git 聯動與自動狀態推進

自動產生包含 Issue ID 的標準 Git 分支名（例如 eng-128-auth-refactor），合併 PR 時自動關閉工單。

4. 10 大跨角色實戰 Prompt

涵蓋產品經理、工程主管、QA、資安與全端工程師等真實研發場景

10 個高階範例
角色 01 技術產品負責人 (PO) · 用戶回饋拆解為 User Story
linear_issue_create

場景情境：客戶訪談中提到「希望匯出報表時可以自選時間範圍與欄位」，PO 需要將其拆解為規格完備的 Linear Issue。 

請使用 linear_issue_create 為團隊「ENG」建立標準 User Story 工單：
1. Title:「[Feature] 自訂時間範圍與欄位之 CSV/Excel 報表匯出功能」
2. Description 需包含：
   - 使用者故事（As a... I want to... So that...）
   - 驗收準則 (Acceptance Criteria, AC 條列 4 點)
   - 前後端技術考量（後端非同步佇列處理大檔案，前端提供進度條）
3. 屬性指派：Priority 設為 2 (High)，預估故事點數 (Estimate) 設為 5 點，加入「Reporting」與「Customer-Request」標籤。
預期成果：AI 調用 Linear 建立格式工整的 Issue，Markdown 格式包含勾選清單 (Checklist) 與清楚指派屬性。
角色 02 敏捷工程主管 (EM) · Sprint Cycle 負載平衡與排程
linear_cycle_manage

場景情境：下個雙週 Cycle 即將開始，需檢視 Backlog 中優先級為 Urgent/High 的工單，根據每位工程師的容量上限 (Capacity) 進行合理分配。 

請使用 linear 工具協助規劃下一個雙週週期（Cycle 42）的排程：
1. 查詢團隊「ENG」待辦清單中 Priority <= 2 (Urgent/High) 且尚未進入 Cycle 的所有 Issue。
2. 計算團隊總容量上限為 35 點 Story Points。
3. 按照前端 (Frontend) 與後端 (Backend) 標籤分組，自動將優先級最高的 Issue 規劃進 Cycle 42，確保總點數不超過 35 點。
4. 輸出排程建議表格，並標註哪些高優先級工單因為容量不足需順延至下下個週期。
預期成果：AI 精算各 Issue 的點數總和，產出平衡的工作量分配建議，防止團隊工程師過勞或承諾超標。
角色 03 QA 測試組長 · 批次建立 Bug 票券與重現步驟
linear_issue_create

場景情境：在 Staging 環境回歸測試中發現 3 個結帳流程的瑕疵，需快速在 Linear 建立規格統一且標記清楚的 Bug 工單。 

請使用 linear_issue_create 批次建立 3 筆結帳模組 Bug 票券：
1. Bug 1:「iOS Safari 結帳時點擊 Apple Pay 按鈕無任何反應」
   - 嚴重度：Priority 1 (Urgent)，標籤：Bug, Mobile, iOS。
2. Bug 2:「促銷代碼輸入小寫時顯示無效，未自動轉大寫比對」
   - 嚴重度：Priority 3 (Medium)，標籤：Bug, UX。
3. Bug 3:「發票統編欄位輸入 7 碼未即時驗證錯誤，送出後拋出 500」
   - 嚴重度：Priority 2 (High)，標籤：Bug, Backend。
每張票券均需包含：測試環境 (Staging v2.4)、重現步驟 (Steps to Reproduce)、預期結果與實際結果。
預期成果：AI 連續建立 3 張格式高度嚴謹的 Bug 票券，包含環境、重現步驟與預期行為，便於工程團隊快速定位修復。
角色 04 Release Manager · 當前週期 PR 狀態盤點與發布清單
linear_issue_search

場景情境：每週四下午發布日前夕，需要盤點當前 Cycle 內哪些 Issue 已經 Done、哪些仍在 In Review，產出精確的發布預告。 

請使用 linear_issue_search 盤點當前活躍 Cycle 的交付狀況：
1. 查詢狀態為「In Review」的所有 Issue，列出其對應的 GitHub PR 連結與負責審查人，提醒今日下班前完成 Code Review。
2. 查詢狀態為「Done」的所有 Issue，按照 Feature (新功能)、Improvement (優化) 與 Fix (修復) 進行分類。
3. 自動產出一份標準結構的「Release Notes v2.5.0 草案」，包含工單編號 (如 ENG-123) 與簡明改動說明。
預期成果：AI 生成清楚的審查催促清單與專業版發行說明 (Release Notes)，大幅省去手動比對 Git 與 Jira/Linear 的時間。
角色 05 技術長 (CTO) · Roadmap 里程碑進度同步與週報
linear_project_update

場景情境：在 Linear Roadmap 更新「Q3 核心架構微服務化」專案狀態，發布健康度評估並向管理階層同步關鍵風險。 

請使用 linear_project_update 為專案「Q3 Microservices Migration」發布本週進度更新：
1. 專案健康狀態：設為「At Risk（有風險）」。
2. 進度百分比：更新為 65%。
3. 內容摘要（Project Update Body）：
   - 本週完成：用戶鑑權與計費模組已成功自單體 (Monolith) 抽離並完成負載測試。
   - 關鍵阻礙 (Blockers)：庫存同步模組因舊版資料庫缺少外鍵限制，資料清洗時間超出預期 3 天。
   - 下週重點：預計動員 2 位資深後端協助資料遷移，爭取下週五前進入灰度測試。
4. 儲存更新並輸出可直接貼到 Slack #exec-updates 的簡報摘要。
預期成果：AI 更新 Linear Project 儀表板，並產出對主管與投資人極具說服力且客觀的高階週報。
角色 06 全端工程師 · 自動領取最高優先級工單並開分支
linear_git_sync

場景情境：工程師早上開始工作，讓 AI 在 Linear 抓出指派給自己的第一順位任務，將其移至「In Progress」並在本地開好 Git 分支。 

請使用 linear 工具協助我開始今天的研發工作：
1. 查詢指派給我 (assignee: me) 且狀態為「Todo」中 Priority 最高的一張 Issue。
2. 顯示該 Issue 的標題、驗收準則與附帶說明。
3. 將該 Issue 狀態推進至「In Progress」。
4. 呼叫 linear_git_sync 生成合乎規範的 Git 分支名稱（例如 feature/eng-145-payment-timeout），並輸出切換分支的 git 指令：git checkout -b [branch_name]。
預期成果：AI 實現終端極速開工流程：自動更新看板、展示需求細節，並生成乾淨符合團隊 GitFlow 規範的分支切換命令。
角色 07 Scrum Master · 燃盡圖 (Burndown) 與團隊速率分析
linear_analytics

場景情境：在雙週 Sprint 回顧會議 (Retrospective) 前，統計近 3 個 Cycle 的實際交付點數與未完成退回率。 

請使用 linear 分析團隊「ENG」最近結束的 3 個 Cycles (Cycle 39, 40, 41)：
1. 統計每個週期的 Committed Points (初始承諾點數) 與 Completed Points (實際完成點數)。
2. 計算團隊平均速率 (Average Velocity) 與承諾達成率 (Completion Ratio)。
3. 列出各週期中最常出現延宕原因的標籤（例如 Technical-Debt 或 External-Dependency）。
4. 撰寫一份供 Sprint Retro 會議討論的改進建議簡報。
預期成果：AI 深度計算歷史速率波動，提供基於數據的敏捷流程洞察，協助團隊找到估點失準的盲點。
角色 08 資安工程師 · CVE 漏洞修補專案追蹤
linear_issue_create

場景情境：安全掃描器發出 CVE-2026-XXXX 重大漏洞警報，需在 Linear 建立緊急安全專案並設定嚴格的 SLA 修補時效。 

請使用 linear 工具建立資安專屬防護專案與緊急工單：
1. 專案名稱：「Security Remediation: CVE-2026-2189 OpenSSL Vulnerability」。
2. 建立母 Issue：「[Urgent] 全面升級基礎 Docker Image 之 OpenSSL 版本至 3.0.15」
   - Priority 設為 1 (Urgent)。
   - Due Date (截止期限) 設為 48 小時之內。
3. 建立 3 個子任務 (Sub-issues)：
   -「Sub-task 1: 更新各微服務 Dockerfile 基礎映像並在本機通過單元測試」
   -「Sub-task 2: 部署至 Staging 並執行自動化滲透迴歸掃描」
   -「Sub-task 3: 安排深夜離峰時間進行 Production 零停機滾動更新」
4. 自動標記指派給 DevOps 團隊主管。
預期成果：AI 在 Linear 建立帶有階層樹狀關係的資安專案與高時效性工單，確保漏洞修補合規透明。
角色 09 客服技術支援 · 客訴自動關聯至 Parent Issue
linear_triage

場景情境：收到多位客戶回報相同的「第三方登入跳出 400 Bad Request」，需在 Linear Triage 收件匣中將這些回饋合併關聯至主工單。 

請使用 linear 工具協助分揀 (Triage) 今日來自客訴系統的新工單：
1. 查詢團隊「Triage」收件匣中所有未分類的新進請求。
2. 比對關鍵字「Google OAuth / 400 Bad Request」，若發現有相同症狀的客訴，自動將其關聯為既有工單「ENG-89: Google OAuth Redirect URI 異常」的關聯回報 (Customer Feedback link)。
3. 在工單內部留言標記：「已合併 4 筆客戶回報，受影響用戶清單：[user1, user2...]」。
4. 提升 ENG-89 之優先級為 High，並通知原負責工程師。
預期成果：AI 智慧合併重複工單，聚合真實受害用戶名單，大幅提高研發團隊定位重大問題的靈敏度。
角色 10 跨部門協調員 · 標定相依性 (Dependencies & Blockers)
linear_relations

場景情境：前端的新功能「線上發票即時預覽」必須等待後端「提供發票預覽 API」完成才能開工，需在 Linear 建立阻礙者 (Blocked By) 關聯。 

請使用 linear 工具為以下兩張工單建立精確相依性關係 (Relations)：
1. 工單 A (FE-55)：「發票預覽前端抽屜 UI 元件開發」
2. 工單 B (BE-102)：「發票即時 PDF 預覽 Stream API」
3. 設定關係：FE-55「is blocked by」BE-102。
4. 當 BE-102 狀態變更為 Done 時，自動觸發機器人通知 FE-55 的指派人「阻礙已排除，可開始前端對接整合」。
預期成果：AI 在工單關聯圖譜中建立阻礙鏈結，有效防範前後端資訊不對稱與停滯等待。

5. 安裝外掛與設定教學

步驟一：於 Antigravity 外掛市場安裝

在 Antigravity 外掛管理員中搜尋並安裝 Linear 官方生態外掛：

antigravity-plugins-partners/plugin/linear

步驟二：設定 Linear Personal API Key

登入 Linear 後前往 Settings > Account > API，產出個人存取金鑰 (Personal API Key)，並配置於環境變數：

# Linear API 存取金鑰
LINEAR_API_KEY="lin_api_xxxx..."

步驟三：連接 GitHub 組織以啟用自動閉環

在 Linear 設定中開啟 GitHub Integration，即可享有 PR 建立自動推進狀態、PR 合併自動關閉工單的完整體驗。

6. 常見問題 (FAQ)

Linear 與 Jira 主要差異在哪裡？

Linear 主打極致輕量、無加載延遲與鍵盤快捷鍵優先，介面極簡直覺；Jira 則偏向巨型企業高度自定義工作流與合規審計。

什麼是 Triage 收件匣模式？

Triage 是團隊的過濾收件匣，所有來自客服、Slack 或非工程人員提出的請求會先暫存在此，經主管或 PO 核可後才會轉為正式 Backlog。

Story Points 估點建議使用何種數列？

Linear 支援費氏數列 (1, 2, 3, 5, 8) 或線性數列。建議團隊採用費氏數列，越複雜的任務不確定性越高，能有效防止估點過於細碎。

如何防止工程師忘記更新工單？

建議善用分支名稱綁定（例如 eng-42-title）與 Git Commit 關鍵字（例如 Fixes ENG-42），由系統全自動推進狀態，免去手動操作。
